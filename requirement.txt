🔴 Các vấn đề chính trong code hiện tại
1. Component quá to (God Component)
 - 1 file làm quá nhiều việc: fetch API, state, business logic, UI, upload, filter, pagination Khó đọc, khó debug
 - Sau 2–3 tháng quay lại sẽ mất rất lâu để hiểu lại flow

2. Logic business trộn lẫn với UI
Ví dụ:
 - generate slug trong component
 - build payload trong component
 - transform filter params trong component
➡️ Vi phạm separation of concerns
➡️ UI không còn “thuần render” nữa

3. State bị phân mảnh và rối
* Dạng như:
 - searchTerm
 - debouncedSearch
 - page
 - pageSize
 - brandFilter
 - categoryFilter
 - startDate
 - endDate
 - selectedIds
 - options states (brandOptions, categoryOptions)
* Vấn đề:
 - Khó trace state flow
 - Dễ bug khi reset filter / pagination
 - Re-render không cần thiết

4. Lặp logic reset page nhiều lần
Bạn đang làm:
setPage(1)
ở:
 - search change
 - filter change
 - date change
 - page size change
➡️ Lặp logic → khó maintain
➡️ Rất dễ quên ở chỗ khác

5. Disable TypeScript (rất nguy hiểm)
/* eslint-disable @typescript-eslint/no-explicit-any */
as any
Hệ quả:
 - Mất type safety
 - API params sai cũng không biết
 - Refactor cực nguy hiểm về sau

6. Fetch options không tối ưu kiến trúc
useEffect(() => {
  fetch brand
  fetch category
}, [])

Vấn đề:
 - Hardcode size 99
 - Không cache
 - Không reusable
 - Component khác cũng phải viết lại y hệt

7. useCallback fetchFn phụ thuộc quá nhiều state [isTrash, debouncedSearch, statusFilter, brandFilter, categoryFilter, ...]
Hệ quả:
 - Re-create function liên tục
 - Dễ trigger refetch ngoài ý muốn
 - Khó đọc dependency graph

8. Selection logic chưa tối ưu
selectedIds.includes(item.id)
Với list lớn:
O(n) mỗi row
Render table 100 dòng = check includes 100 lần
Nên dùng Set để O(1).

9. Magic values & hardcode
Ví dụ:
size: 99
"Tất cả"
string filter keys: "status", "brandId"
➡️ Khó scale & dễ typo bug

10. Error handling chưa chuẩn hóa
Hiện tại:
catch (error: unknown) {
  const err = error as Error;
  toast.error(err?.message || "Có lỗi xảy ra!");
}

Vấn đề:
Lặp lại ở nhiều function
Không phân biệt API error vs network error

11. Debounce thủ công nhưng chưa tối ưu
setTimeout(() => setDebouncedSearch(searchTerm), 500)
Nhược điểm:
 - Lặp lại logic debounce
 - Không reusable cho các table khác
 - Không cancel request cũ (race condition)

12. Tính tái sử dụng thấp (dù nhìn có vẻ generic)
Dù có:
 - useTableManager
 - useApiData
Nhưng vẫn:
 - Gắn chặt với Product logic
 - Filter config hardcode theo product
 - Service gọi trực tiếp trong component
➡️ Khó dùng lại cho: Orders, Users, Categories…

🟢 Cần tối ưu để code dễ đọc & tái sử dụng hơn (ngắn gọn)
 - Tách rõ: UI logic ≠ business logic
 - Gom các state liên quan thành 1 object (filterState)
 - Chuẩn hóa API params builder (tránh lặp mapping filter)
 - Dùng Set thay vì Array.includes cho selection
 - Không dùng any / bỏ ts-nocheck
 - Tránh hardcode size, string key, magic values
 - Chuẩn hóa error handler (1 pattern duy nhất)
 - Giảm dependency phức tạp trong useCallback
 - Tránh lặp setPage(1) ở nhiều handler
 - Chuẩn hóa debounce (reusable thay vì inline)
 - Giảm số lượng useEffect rời rạc
 - Giữ component chính chỉ lo: orchestrate + render
